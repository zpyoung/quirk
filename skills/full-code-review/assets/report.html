    `--repo` is never threaded to reconcile/check, breaking branch and local memory

    src/inventory/ledger.py:857

    Branch and local reviews silently lose their memory, so every prior finding comes back as new and remembered decisions are dropped.

    load is the only subcommand that accepts --repo. reconcile and check do not, so validate_snapshot's repo parameter falls back to "." — the process's cwd. SKILL.md invokes load with --repo "$REVIEW_SOURCE_ROOT" but invokes reconcile/check through a path relative to the skill's own directory, with no --repo and no cd.

    For branch and local targets, _target_identity calls _repo_identity(repo), which reads git config --get remote.origin.url at that path. The identity computed during reconcile is therefore derived from the skill directory rather than the repo under review, so it disagrees with the identity load computed, and validate_snapshot raises ValueError("memory snapshot identity does not match review context"). The memory feature fails for every branch and local author-seat review. check_plan (line 816) hardcodes validate_snapshot(snapshot, context, ".") and has the same defect, so the author check step documented in posting.md fails the same way.

    Change-request reviews are unaffected because _target_identity never touches git when change.number is present — which is also why the test suite, which exercises only the PR path, cannot see this.

    This and the untested branch/local identity path below are the same blind spot seen from two directions: the bug exists precisely because no test ever leaves PR mode.

    Two unrelated reviews running at once block each other on every ledger save, and each save gets slower as the ledger grows.

    Summary

    The feature is coherent and its security boundary is genuinely well built — untrusted forge note text never drives a posting decision, and the flow fails closed before any mutation. One defect blocks it: --repo is never threaded to the reconcile and check subcommands, so memory breaks outright for every branch and local author-seat review. The suite cannot see it because every test stays in PR mode, which is also the largest of the coverage gaps below.

    Risk Low

    LikelihoodOccasionalA false-positive fingerprint match in the new suppress_post branch would drop a legitimate finding with no visible error.
    ImpactNo IncidentPersonal plugin tooling; worst case is a duplicate or missing review comment.
    Blast radiusNarrowScoped to the user's own review workflow — no merchant-facing path.
    DetectionModerateSuppressions are recorded in the staged state before any mutation, but stage() still reports success when the ledger save was refused.
    RollbackCleanRevert the PR; the ledger is local state under ~/.local/state and is never read by anything else.

    Lowering this risk

    The design already carries its own best mitigation: stage records every suppression's reason and thread_url in the staged state before publish --confirm touches the forge, and _prepare_memory_report raises before any draft is created when snapshot validation or the discussion fetch fails. That makes the feature fail closed and every suppression visible pre-mutation, which is why no additional risk-reduction technique is recommended. What would move the rating is narrowing the likelihood term specifically: the fingerprint collision test and the binding-mismatch test below attack exactly the false-suppression path that drives it.

    The fail-closed claim is proven only against a fake

    The 78 new tests exercise the known edge cases — author-identity check, late-duplicate block before bulk publish, snapshot binding — but entirely against FakeForge, never against real note bodies. The identity gate itself is sound on inspection; what is untested is its behaviour on live data.
